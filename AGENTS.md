# Project: Realm

## General Project Overview:
- RTS Game using Godot with C# and a custom Flat Bitmask Structure-of-Arrays (SoA) ECS shared directly with WASM linear memory.

## Overall Coding Style:

- Prefer functional programming paradigms where appropriate.
- All code, variable names, and comments must be written in English.
- Do not add comments anywhere unless explicitly requested.
	- Structs in the `Realm.Ecs` project must have a single XML-doc `<summary />` comment at the top describing their purpose.
	- Everything in `Realm.MapAPI`, `Realm.EditorAPI` and the map-script handles and primitives in `Realm.Ecs/Shared` must have full, comprehensive XML-doc comments for public consumption.
- Do not use `#region` blocks.
- All code should be self-documenting. Use verbose, descriptive names that clearly identify their purpose (avoid cryptic abbreviations).
- Avoid the `sealed` keyword.
- Use [GeneratedRegex] syntax.
- Avoid keywords `internal` and `InternalsVisibleTo` use `public` or `private` instead.

## Core 3D rendering and Engine Tick Calculations:
- Minimize Garbage Collection (GC) pressure by using struct-based data where possible.
- Highly optimized godot simulation tick handlers: Do not allocate new objects, do not manipulate strings, do not use lambdas that capture variables. Prefer reusing collections, employing object pools.
- Utilize high-performance .NET structures like `Span<>`, `ReadOnlySpan<>`, and `StringBuffer` especially when transferring structural buffers between Godot and C#.
- Use `System.Numerics` to enable SIMD mathematical operations and vector arithmetic where possible.
- Prefer Enums over Strings

## Match Cadence, Snapshot Size and Compression:
- Simulation tick: **30 Hz** (`MatchTiming.SimulationTickRateHz`). Fast enough to feel responsive while leaving headroom for slow machines and high unit counts.
- Snapshot send rate: **30 Hz, equal to the tick rate** (`MatchTiming.SnapshotRateHz`).
- Compression: **Zstandard level 1 for both deltas and baselines** (`SnapshotWireFormat.DeltaCompressionLevel`). Stronger compression will cause higher CPU overhead with minimal bandwidth reduction.

## Networked Movement Presentation and Latency Masking:
The client renders the authority's own timeline. It does not simulate or predict. Rollback and determinism are not supported. Latency masking cannot be considered game truth.
- **snapshot interpolation** (a buffered sample at a cursor behind the newest description, `SnapshotTimeline.TrySample`). The cursor advances per rendered frame, not per simulation tick, so `GameHost.AdvancePresentationForRenderFrame` runs from `_Process` and every replicated unit is placed once per drawn frame.
- **presentation delay** (how far behind the cursor runs). It is measured, not guessed: the shortest recent one-way trip the latency probe has shown sets the floor, its jitter widens the ceiling, and running out of descriptions deepens it. The floor is clamped to `SnapshotTimeline.MaximumDelaySequences`, which is what a link up to about 1.2 s of round trip can be masked on. Every peer is held at the depth its own measurement asks for, including one whose authority is the process it launched itself: a match on loopback measures a trip that rounds to the minimum depth, so it is held there by the same rule as a screen across a network, where a formula that is about to be wrong for everybody is cheapest to notice. A buffer that runs dry holds the cursor at the newest description rather than moving it backwards. A sample that a description genuinely places behind where it was last drawn — the frame a completion releases an extrapolated lead — is given back at a bounded speed rather than in one frame, so the catch-up reads as settling instead of as a jump.
- **confirmed-order extrapolation** (a unit the local player owns that carries a replicated `MoveTo` is drawn one snapshot interval ahead of the cursor, which masks exactly that interval of the delay for that unit, along the direction the authority was already moving it; while the buffer covers the interval the step is interpolation between descriptions already held, and only past the newest description does it become a guess, bounded to one interval and 0.75 m). Another player's unit is never drawn ahead of its description, because that would invent motion this screen was not told about. The lead is eased over a duration, and it is released by the description the cursor is showing rather than by the newest one held, so it lasts until the completion is drawn.
- **route preview** (a path drawn for an order the authority has not answered yet, which writes no position).

## Godot-Specific Coding Rules:
- 2D button: always specify the `icon_max_width` property.
- Localization keys are generated by scanning for `TranslationServer.Translate("literal")`, and a key with no such call site is pruned from `locale/en.json` on the next build. A literal handed to a method that translates internally (such as `InGameHUD.ShowFeedbackText`) must still be wrapped in `TranslationServer.Translate(...)` at the call site, or its key will not survive.
- Godot nodes should only include UX logic, domain logic should be delegated to services
- For any text labels that appear on screen, ensure they are translated via `LocalizationManager.cs`.
- Labels in Containers: When setting autowrap_mode, always set custom_minimum_size.x (explicit width) and size_flags_horizontal = SIZE_EXPAND_FILL. Otherwise Godot calculates custom_minimum_size.y based on single-word wrapping, causing container to stretch excessively tall.
- Unicode Icons: Never hardcode `\uXXXX` escape sequences inside string literals in UI or HUD scripts. Always reference named glyph constants defined in `UnicodeIcons` (e.g. `${UnicodeIcons.UPLOAD}`).
- `[GlobalClass]` Registration: Every custom non-generic, top-level C# class that inherits from `GodotObject` (`Node`, `Node3D`, `Control`, `Resource`, etc.) must be marked with the `[GlobalClass]` attribute so it registers as a distinct type in Godot's ObjectDB and profiler rather than falling back to its native C++ base class.
- Explicit Node Naming: Whenever instantiating a generic Godot node (`new Node3D()`, `new PanelContainer()`, etc.) or scene prefab (`.Instantiate()`) in C#, immediately assign a descriptive `.Name` property identifying its purpose or source system to prevent anonymous `@Type@####` or `Type_####` entries in the SceneTree and ObjectDB profiler.
- Node Lifecycle & Cleanup: Never leave detached nodes in memory. When removing a node via `RemoveChild()`, either explicitly call `QueueFree()` on it or return it to a managed object pool that properly frees all pooled instances on cleanup.
- One-Way C# to Godot Transform Pipeline: Avoid unnecessary c# to godot c++ marshaling. Treat ECS as the source of truth. Never read fields such as `Position` from godot nodes when available in ECS. Batch update godot fields in a single `Transform` when possible and only update if field is dirty.
- Don't enable `_Process` overrides on node subclasses with many instances, instead code a centralized manager for active entities to handle per-frame updates in bulk.
- Menu scene 2D UX images should be downscaled to their maximum rendered size and encoded with cwebp 90 quality with this .import file value to avoid re-compression in PCK file: importer="keep"

### Realm.ECS Data Layer (Flat Bitmask SoA Shared Memory):
- Core simulation component buffers (`PlayerResource`, `Health`, etc.) are implemented as a custom Flat Bitmask Structure-of-Arrays (SoA) ECS where component arrays are stored in contiguous unmanaged memory mapped directly into WASM linear memory (`Wasmtime.Memory`).
- Only the authoritative process simulates. `GameHost.cs` renders the replicated world it receives: its physics tick applies snapshots and runs the client tick, and its render frame places every replicated unit on the presentation cursor. It never steps authoritative data, only cosmetic.
- The client and authority data are stored in separate processes to prevent direct access without replication.
- Do not store Godot lifecycle elements, scene nodes, or UI references directly inside ECS components. Components must remain pure unmanaged, blittable data structures (`[StructLayout(LayoutKind.Sequential, Pack = 4)]`).
- Entity creation, lifecycle recycling, and queries use hardware bit manipulation (`BitOperations.TrailingZeroCount`) over entity bitmasks for zero-allocation performance.

### Logic Services:
- Classes inheriting from Godot should have minimal orchestration logic, deferring complex logic to domain-specific services.
- Decoupled Communication: Avoid using DTOs to communicate between orchestrators (`GameHost`) and services. Communication should be minimal and limited to simple ephemeral primitive parameters and return values. All persistent shared data must be stored directly in the ECS, allowing both services and `GameHost` to query and write to the ECS independently to coordinate.
- Services should never be instantiated directly, they should always be accessed via the global GameContext. `GameContext.Simulation` is this process's own world and services, so the same service type exists once per process and never spans the process boundary.

### Realm.MapAPI & WASM Zero-Allocation Shared Memory Architecture:
- Only expose safe APIs to map authors and external tools to prevent direct manipulation of raw Godot nodes or C# ECS structures.
- All map scripting operations proxy through `IGameAPI`, while map editing operations proxy through `IEditorAPI`.
- Editor operations belong on `IEditorAPI` (`Realm.EditorAPI`) and are implemented by `EditorService`, never grown on `GameHost`. The interface is the editor's remote-control surface: a tool, a DLL consumer or an MCP server reaches the editor only through it, by method name, so every operation must report an `EditorOperationResult` rather than relying on on-screen feedback.
- APIs must generate zero heap allocations and zero GC pressure.
- Do not use `yield return` keyword inside WASM layer because it compiles to a GC heap allocation.
- Use `ReadOnlySpan<T>` over facade types for enumeration rather than `T[]` or `List<T>`.
- Everything in `Realm.MapAPI` (including `IGameAPI` and `IEditorAPI`) must have full, comprehensive XML-doc comments for public consumption.
- Zero-Allocation Facade Pattern & 0ns Direct Reads:
	- `IGameAPI` should strictly require integer IDs as parameters, never full objects.
	- Facade handles exposed to map scripts (`PlayerId`, `UnitId`, `ResourceNodeId`, `LootItemId`) are plain index structs in `Realm.Ecs` defined as `readonly record struct PlayerId(int Value)` with implicit type-cast 'FROM int' but NEVER 'TO int'.
	- Primitive property getters (`get => EcsSharedMemory.PlayerResources[Value].Gold;`) perform **0ns direct memory reads** straight from the shared WASM linear memory ECS arrays without crossing the host boundary.
	- Property setters (`set => HandleCommands.Current?.SetPlayerGold(Value, value);`) and commands route through authoritative Host imports, executing full domain rules and side-effects in-place. A settable property stays an instance member on the handle rather than an extension member, because only an instance setter may be assigned through a `foreach` iteration variable or a `ReadOnlySpan` element.
	- Everything else a script calls on a handle — reads that need the host and every order, cast and effect — is a C# 14 extension member supplied by `Realm.MapAPI`.

### Map Workspaces & WASM Compilation (Portability):
- A map's WASM is produced by the editor's workspace publish and shipped inside the map folder next to its metadata. The authority executes exactly that artifact and nothing recompiles it at match time, so every host of the same map runs the same canonical bytes. The client never loads a map assembly.
- The loaded map folder is its own workspace and is compiled to WASM via `dotnet publish`. There is no separate temp workspace: the folder the user opened is the source of truth, and it MUST stay machine-portable, so never write absolute paths into generated/saved `.csproj` files.
- Version history is an editor-only sidecar: `MapHistoryService` keeps an internal LibGit2 repository per map under `%LOCALAPPDATA%\Realm\map_history`, keyed by the map name so folders of the same map share one history. It has no remote, never writes inside the map folder, and a map author's own `.git` inside the folder is excluded from history, publish and export. Nothing in the match path reads it.
- `MapWorkspaceService.EnsureCsproj` always normalizes the `Realm.MapAPI` and `Realm.Ecs` references to the relative `<HintPath>lib/Realm.MapAPI.dll</HintPath>` and `<HintPath>lib/Realm.Ecs.dll</HintPath>`, and `EnsureApiLib` copies both DLLs (build output preferred, `MapTemplate/lib` as fallback) into the workspace so it is self-contained. A workspace also carries `<Using Include="Realm.Ecs" />` so a map script keeps writing `using Realm.MapAPI;` while still naming the shared simulation handles.
- `MapTemplate/lib/Realm.MapAPI.xml` and `MapTemplate/lib/Realm.Ecs.xml` are the committed API documentation beside those DLLs. When changing `Realm.MapAPI` or `Realm.Ecs` source, rebuild it (`dotnet build Realm.MapAPI`) so the `CopyToMapTemplate` target refreshes the whole of `MapTemplate/lib`, and commit the refreshed documentation together with the API changes.
- Simulation primitives below the script surface (`ComponentIds`, `ComponentMask`, `EcsSharedMemory`, `ContentIdStore`, `StringRegistry`, `SeededRandom`, `HandleCommands`, the map script handles) live in `Realm.Ecs`, and the script surface a handle offers on top of them is supplied from `Realm.MapAPI`. `Realm.Ecs` never references `Realm.MapAPI`.
- A map folder carries two compiled scripts, both in `bin/script` (`MapFileService.ScriptOutputDirectoryName`): `<Assembly>.wasm`, the optimized build every match runs, and `<Assembly>.debug.wasm` (`MapFileService.DebugScriptNameInfix`), the build carrying DWARF that only a playtest attaches a debugger to. Each build publishes into `bin/.build-<flavor>` and is moved into place under the name its flavor gives it (`MapFileService.ScriptFileNameForFlavor`), so compiling one flavor never disturbs the other and a failed compile leaves both as they were. The artifact's own name is what states its flavor; the retired `bin/script/.build-flavor` marker is not written any more and is removed when one is found. Nothing searches `bin` for the newest `.wasm`: the authority asks for the flavor the match needs (`ServerMapScript.TryFindScript`), and a map that has no build of that flavor runs the other one and says so in its log. A workspace built under the older per-configuration folders is repaired by `MapWorkspaceService.EnsureSingleScriptOutput` on its next compile, which moves the last artifact into `bin/script` under the name its debug information gives it and removes the folders it came from.
- Only `btnTestMap` compiles `Debug`, which embeds DWARF so a debugger can attach; `btnPublish` and `_btnExportMap` always compile `Release`, which strips it. The unchanged-sources shortcut is taken per flavor, against that flavor's own artifact, so publishing straight after a playtest recompiles the optimized build instead of shipping the playtest bytes. A playtest that compiles newer sources deletes the optimized build left behind by an older source tree, so nothing in the folder can run code the author has already changed; until it is rebuilt for release, a match runs the playtest build and reports that it did. Exports, packages and manifests never carry `<Assembly>.debug.wasm`.
- `MapTemplate/lib/Realm.MapAPI.pdb` and `MapTemplate/lib/Realm.Ecs.pdb` are load-bearing for map debugging: the script compiler reads a referenced assembly's line information from the symbols beside it, so without them a map script compiled in that workspace steps through `GameAPI` and `EcsSharedMemory` with no source lines. `EnsureApiLib` copies both into every workspace for that reason. `Realm.EditorAPI.pdb` is in no map script, so the published build trims it and the client's own copies of these symbols, which is what the workflow step `Keep Only the Symbols a Map Debugger Reads` does; the authority keeps its symbols because the log it writes names the line a failure came from.
- Shared map folders are portable when they contain a relative `.csproj` and the `lib/` folder. Saved/opened map folders are auto-repaired by `EnsureCsproj` on the next workspace setup.

### Steam Surface for Map Scripts (Opt-In):
- `IGameAPI`'s Steam members (`Realm.MapAPI/IGameAPI.Steam.cs`) let a map unlock achievements, indicate progress, record int/float stats and keep per-player cloud files. The engine never calls them: a map that says nothing about Steam behaves exactly as before.
- The authority has no Steamworks, so an achievement, a stat or a cloud write is written as a `PresentationKind.Steam*` request addressed to the player slot, which only the screen sitting in that seat applies (`SteamScriptBridge`, which namespaces the identifier with `SteamScriptNames.ForMap` before Steam sees it). Audio-visual ordering does not apply: these travel on the reliable stream because they are state, not moments.
- Cloud reads are a round trip, not a synchronous call: `RequestSteamCloudFiles` asks the seat's screen for its files, the screen answers with a `NetworkFrameKind.SteamCloudUpload` frame carrying the request's handle, `ServerSteamCloud` keeps that copy per seat (older answers are dropped), and `IsSteamCloudSynced`/`ReadSteamCloudFile` read it. Writes and deletes update that copy as well as reaching Steam.
- A seat counts as being on Steam when its own hello stated a SteamID64 (`ServerSimulation.SetPeerSteamId`), so computer seats, unheld seats and screens without Steam answer `IsSteamAvailable` false and every other Steam call is a no-op for them.

### Cinematic Camera Surface for Map Scripts (Opt-In):
- `IGameAPI`'s camera/cinematic members (`Realm.MapAPI/IGameAPI.CameraCinematics.cs`) let a map take a player's camera for a shot (`MovePlayerCameraTo`, `FollowUnitWithPlayerCamera`, `StopPlayerCameraFollow`, `LockPlayerCamera`), give it back (`ReleasePlayerCamera`), and dress the screen (`SetCinematicBarsVisible`, `ShowCinematicSubtitle`, `SetScreenFade`). The engine never takes a camera on its own, and nothing in the match changes while it is held. `IGameAPI.EveryPlayer` addresses every screen, which is what a co-operative cutscene uses.
- The camera half lives in `CameraControl.Script.cs`: a `MoveTo` shot looks at the point it was given for the whole move (a cut when the duration is zero), a `FollowUnit` shot sits at a stated distance/height/bearing behind a unit and looks at it, and both keep the camera above the terrain and write the reading back into `CameraState` so the HUD, the minimap and the player's own controls continue from where the shot left the camera. The player's input path is skipped entirely while a map drives the camera.
- The dressing half is `CinematicOverlay`, a `[GlobalClass] CanvasLayer` created as a child of the match host the first time a map asks for it, so it leaves the tree with the match. It draws the bars, one subtitle line with its speaker, and a fade that covers the HUD as well.
- A shot that names a unit this screen is not drawing yet (`SetPendingScriptFollow`) waits for the description that does, rather than being dropped or asked for twice.

### Map Script Debugging (Attach to the Authority):
- A map script runs inside the authority, so a debugger attaches to `Realm.ListenServerHost`, never to the Godot client. There is one target process per match and it is the one the script is executed in; no screen reports a PID to attach to.
- A match started with its script in debug mode keeps the script's DWARF and exports the Wasmtime JIT ELF into the workspace the start command names, as `<workspace>/MapScript.jit.elf`, which is the module the workspace `.vscode/launch.json` loads. `wasmDebug` and `mapWorkspacePath` travel in the control command that starts the match, never on the authority's command line, because the authority is already running when the match arrives. The authority logs its PID, its workspace and every ELF it exported. Both are opt-in: a normal, dedicated or exported match runs its script compiled for speed and writes no debug artifact.
- The editor's `btnTestMap` asks for both itself, because the playtest is played straight out of the workspace that was just compiled. A map folder opened on its own still works: the authority works the workspace out from where the script sits.
- `.vscode/launch.json` (`Attach to Realm Authority (Map Script WASM)`) and `realm_lldb.py` are copied from `MapTemplate` on every workspace setup and refreshed again before every map compile, so an existing workspace is repaired on its next open or test. `MapTemplate/realm_lldb.py` is generated from `Realm.WasmBindgen/realm_lldb.template.py`; the generator discovers every handle type, component layout, component offset and host wrapper from `Realm.Ecs` and `Realm.MapAPI` source, so a new handle, component or API property is reflected on the next build without editing a list. Handle properties that read shared memory are shown as real values, and properties that cross the WASM boundary show the inspection tooltip instead of a backing-field pointer.
- The workspace debugger script also provides `realm_doctor`, `realm_verify`, `realm_version`, `realm_inspect`, `realm_watch`, `realm_plot`, `realm_export`, `realm_step`, `realm_reload`, `realm_attach`, `realm_where` and `realm_exception`. `realm_inspect` also walks NativeAOT managed references: `WebAssemblyRefWrapper<T>` and `WebAssemblyPtrWrapper<T>` are translated from guest linear-memory offsets to host addresses using `wasmMemoryBase` in `MapScript.debug.json`, and `List<T>` and `T[]` values expose `Count`/`Length` plus indexed elements, while `System_String` decodes its UTF-16 characters to the actual text. `realm_doctor` checks the PID, debug metadata, JIT ELF, shared-memory base and component tables; `realm_verify` reports generated/runtime table drift; `realm_inspect` prints every field of a handle; `realm_watch` records a field on each stop and `realm_plot`/`realm_export` render or export the samples; `WasmScriptHost.ExportJitDebugElf` repairs the JIT ELF's DWARF range and location-list gaps for map-script functions before writing it, so LLDB can resolve line-table addresses and inspect locals the raw JIT dump leaves outside a compile unit; `realm_step` is disabled because CodeLLDB cannot resume from a Python command, so normal F10 is the supported path; `realm_break` sets a breakpoint at every statement address for a file and line, which works around LLDB choosing a cold-path line-table entry; `realm_recover` selects the nearest user frame when the debugger is stuck without an active source line; `realm_just_my_code` selects the nearest user frame on each stop instead of resuming; `realm_reload` re-imports the script; `realm_attach` accepts a PID or falls back to `authority.pid` and a `Realm.ListenServerHost` process scan; `realm_where` prints the nearest user frame; and `realm_exception` toggles stopping on WASM traps.

### Map File Format & Zero-Fallback Policy:
- Strict Canonical Schema: Runtime loaders, parsers, and editor services must maintain zero fallback paths and strictly expect canonical variable names and data structures. Never add backwards-compatibility fallbacks, casing aliases, or fallback-to-template shims in runtime loading logic.
- Map Migrations (`MapUpgradeService.cs`): Backwards compatibility for older maps is handled exclusively via sequential `IMapMigration` classes inside `MapUpgradeService`, modeled after Entity Framework Migrations. Each release build only transitions from the immediate prior version (`v0.0.0 -> v0.0.1 -> v0.0.2...`), allowing multi-version outdated maps to upgrade sequentially in sequence.
- `GameBuildNumber`: Every `metadata.json` must include a `GameBuildNumber` string matching `RealmVersion.GameBuildNumber`. This value is hardcoded and only changed manually when publishing and tagging an official release. Matches in the game lobby are locked to the map's `GameBuildNumber`.

### Map Authoring Surfaces (Schema & vsCodium Realm.MapEditorExtension):
- One generated vocabulary, no hand-written UI metadata: `metadata.schema.json`, `terrain.schema.json` and `manifest.schema.json` are auto-generated by `RealmJsonSchemaExporter` at compile time
- The document is the single source of truth. The text editor and the form read the same `TextDocument` and cannot keep a separate parsed in-memory model (to avoid sync issues with godot process running `MapEditorHUD`).
- Adding a field is a model change, not an extension change: a C# property with the right attributes plus a regenerated schema must appear correctly in the text editor, diagnostics, completion and the form with zero edits in `Realm.MapEditorExtension`. An extension edit required for a new field is a design error, unless that edit adds a new schema vocabulary keyword.
- The form is a presentation of the schema, not a feature fork: anything it can do to a field must be expressible for any field from the schema alone. Never grow a form-only capability the text editor cannot express, and never let the two surfaces diverge in what they permit.

## Client and Server Process Split:
- `Realm.Client` must never have a compile-time project reference to `Realm.ListenServer`, and no `using Realm.ListenServer` may appear in its source. `Realm.ListenServer` must never reference `Realm.Client` or Godot. All gameplay communication crosses the process boundary as serialized transport frames; there is no shared in-process world, service, or static state between them.
- The one assembly reference allowed is build ordering: `Realm.Client` carries a `ProjectReference` to `Realm.ListenServerHost` with `ReferenceOutputAssembly="false"` so a development build always produces a current authority beside the client. Nothing is linked against it, and it is not a way to call into the authority.
- `FrameDelivery.UnreliableOrdered` carries every delta, split across datagrams (`SnapshotFragment`, `MaximumDatagramBytes`) when one is too large for a datagram, because a delta describes a world the next delta supersedes. `FrameDelivery.Reliable` carries baselines, repairs and everything else the match cannot proceed without. A delta must never be moved onto the reliable stream for its size: there it holds every description queued behind it, and that head-of-line stall is what costs a peer the whole run.
- A description that does not arrive is repaired by name, not by rebuilding the world. The match keeps the last `SnapshotFrameRing.Capacity` descriptions it sent each peer and answers a `SnapshotRepairRequest`, or a hole its acknowledgement reports, with exactly those. The client holds a description that arrived ahead of a missing one and asks for the run, because a delta states only the units that changed since the description before it; applying one across a hole leaves exactly those units behind. A baseline is the fallback for a run the ring no longer holds, and carries its own reason code in the traffic report.
- The client never runs WASM and does not reference `Realm.MapAPI` or `Wasmtime`. Map scripts, `IGameAPI`, `EcsSharedMemory` and the `Wasmtime` host live only in the authority. The editor compiles a map to WASM and the authority executes that artifact; `IEditorAPI` (`Realm.EditorAPI`) remains the client's map-editing surface and is unrelated to `IGameAPI`.
- Authority-only components are never replicated, and the wire component ids are part of the handshake (`wireTableHash`). Adding a replicated component means adding it to the canonical table in `Realm.Ecs.Replication.ReplicatedComponents`.
- One authority process per screen, started when the game starts and kept for the whole session (`Realm.Client/Services/LocalAuthority.cs`). Matches are put on it, paused and replaced through `ServerControlProtocol` over its standard input, and its control commands are applied on its main thread; it is never started per match and never killed between them. Leaving a match, or joining somebody else's lobby, pauses the authority: the match and its socket are given up and the process stays up, so it serves every session until the screen ends and only ends with it.

## Match-Critical Concurrency & Thread Ownership:
- **Scope:** These rules apply to everything a match runs on the clock: authority simulation and snapshot publishing (`Realm.ListenServer`), and the client's match path (`GameHost`, network channel, presentation, and in-game HUD) excluding editor, menus, asset distribution, and other non-match-critical tooling.
- **Ownership over synchronization:** Every shared mutable resource, including static fields, must have an explicitly designated owner, a single writer, and a defined lifetime. Prefer ownership-based designs, immutable snapshots, double-buffering, and atomic publication (`Interlocked` / `Volatile`) over locks and shared mutable state.
- **One writer per world:**  Each EcsWorld has exactly one writer lane, and no world is ever written from two. Parallel work within a tick must use explicitly assigned work and output slots. Workers may read shared state and write only to their assigned outputs; ECS mutations are applied by the simulation thread after synchronization, in deterministic index order. Never perform structural changes or grow component buffers while parallel workers hold references or spans into them.
- **Non-blocking execution:** No match-critical thread may block waiting for a shared resource, lock, semaphore, blocking collection, synchronous I/O, or another lane's progress. Simulation ticks, snapshot publishing, network processing, presentation, and render ticks must not be extended by resource contention or unpredictable external work. Intentional fork-join synchronization within a tick is permitted only for bounded, explicitly budgeted work. Work that cannot complete within its budget must be deferred, coalesced, or dropped according to the relevant system's correctness requirements rather than blocking the match.
- **Immutable handoff and asynchronous publishing:** Never hand off data that another thread may still modify. Data transferred between simulation, snapshot publishing, transport, and presentation must have explicit ownership and remain immutable for the duration of consumption. Snapshot generation and publishing must not make the simulation thread wait for workers, borrowed buffers, or publication completion. Prefer transferring ownership of completed buffers or publishing immutable snapshots, with explicit buffer lifetime management. Define overload behavior so publishing cannot accumulate unbounded work or violate replication ordering and delta dependencies.
- **Static mutable state:** Audit static mutable fields whenever introducing or modifying match-critical functionality. Static state is shared within a process and must follow the same ownership, single-writer, and lifetime requirements as instance state. Never assume a singleton, static registry, cache, or object pool is inherently thread-safe.
- **Godot thread affinity:** Keep nodes, Multiplayer peer management, and other main-thread-owned Godot operations on the main thread. Background workers should operate on primitives and independently owned buffers, returning results through a controlled main-thread handoff such as `CallDeferred`. Only perform other Godot operations on background threads when their specific APIs explicitly guarantee thread safety.
- **No blocking logging or I/O:** Simulation and other match-critical handlers must never perform synchronous disk I/O, including logging, replay recording, or file operations. Use bounded, preallocated producer-consumer buffers drained by dedicated background consumers. Define explicit overflow behavior; never block a producer waiting for logging, recording, or disk throughput.
- **Synchronization exceptions:** A synchronization primitive must never be introduced as a default solution. Any lock, reader/writer lock, concurrent collection, or other synchronization mechanism reachable from match-critical code requires explicit justification of its contention characteristics, memory visibility guarantees, blocking behavior, and resource lifetime. Prefer immutable copy-on-write publication for read-heavy shared data. Use `ReaderWriterLockSlim` only when immutable publication is impractical and its contention characteristics justify it. Never hold locks across `await`, I/O, callbacks, Godot calls, or calls into another execution lane. Avoid nested locks and lock-order dependencies.

## AI "Vibe" Coding & Maintenance Instructions:
- Avoid using proprietary or copyrighted terms from other games.
- For fast lookup during queries without breaking the PURE DATA PRINCIPLE, do not put Godot Nodes inside components. Instead, map the relationship using unique entity IDs, or look up corresponding visual nodes via a managed registry outside the ECS system arrays.
- Don't write unit or integration tests unless explicitly instructed to do so.
- Always compile code after making changes to ensure there are no errors.
- Do not code backwards compatability of fallbacks when adding new features or refactoring, it is the map author's responsibility to upgrade to the latest format (with the help of `MapUpgradeService`) and old maps can continue to be played on old game builds.

- Don't run tests unless explicitly told to do so
- The adapter needs `GODOT_BIN`; on this checkout Godot 4.7 mono lives at `C:\Program Files\Godot_v4.7-stable_mono_win64\Godot_v4.7-stable_mono_win64.exe` (there is no `godot` on PATH). Without it every suite fails with "Godot runtime is not configured".
- Method-level `--filter` works for the logic suites, e.g. `--filter "FullyQualifiedName~MultiplayerEcsSyncTests.CleanTwoPeerRunKeepsBothClientsConverged"`; the unfiltered run discovers all 8 suites (60 tests) and starts normally.
- The scene-based suites (`MapEditorUxTests`, `UxSceneTests`) cannot run as the test project is laid out. They load `res://GameHost.tscn` and `res://Assets/UI/*`, which only exist when the Godot project root is `Realm.Client/` (that is where `project.godot` and its `[dotnet] project/assembly_name="Realm.Client"` live). The adapter always launches Godot in `Realm.Client.Tests/`, which has no `project.godot` and therefore no assembly name, so Godot reports `Cannot instantiate C# script ... res://gdunit4_testadapter_v5/GdUnit4TestRunnerScene.cs`, then the adapter gives up with `Failed to connect: Connection timeout`. Compiling that script into the test assembly and clearing `.godot/mono/temp` both leave it broken. Running these suites needs the test sources to live inside the `Realm.Client` Godot project, or a test project that can see the game's `res://` - a layout decision, not a flag. So UI-test changes cannot be verified by test here; verify them by building and by running the game.
